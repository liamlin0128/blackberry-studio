- 页面：轨道管理正常态，以及定轨配置、历史轨道、定轨结果弹层。
- 证据：`C:\Users\lilin\Downloads\轨道计算真实系统html\轨道管理2.html`、`C:\Users\lilin\Downloads\轨道计算真实系统html\轨道管理3.html`、`docs/evidence-inventory.md`；实现核对 `src/App.css`、`src/pages/OrbitTrackManagePage.tsx`、`src/features/orbit-track/OrbitTrackDialogs.tsx`。
- 独立性：未查阅其他专家的意见单或汇总文件，未修改应用代码。
- 评审限制：本次仅完成静态 HTML/源码核对；当前自动化浏览器不可用，未把未执行的 1440px、1280px、1024px 视觉走查标记为通过。以下“需处理”均为证据支撑的视觉保真风险；“建议”不构成需求或业务变更。

## 意见

### V-01 — 左侧导航的宽度与节奏偏离原系统【需处理】

- 分类：布局
- 原意见：当前壳层的左侧栏明显比原系统宽，且分组/叶子项的垂直节奏被放大；在同一框架菜单中切换时，会削弱与任务控制系统的连续性。
- 证据：原系统快照的侧栏容器显式为 `width: 210px`；当前 `src/App.css` 将 `.system-brand`、`.side-nav` 固定为 `247px`，分组和入口分别为 `42px`、`38px`。`docs/evidence-inventory.md` 已将 SP-MCS 顶栏和轨道计算侧栏列为需复用的统一壳层。
- 建议：将默认桌面宽度校准到原快照的 210px，并以原系统菜单项实际行高复核分组与叶子项；若产品决定沿用任务规划系统的 247px 壳层，应在阶段 3 规范中明确“跨分系统标准化差异”，不要将其表述为原样还原。

### V-02 — 顶栏品牌资产与原系统不一致【需处理】

- 分类：视觉
- 原意见：原系统使用 SP-MCS 图片 Logo 与用户头像，原型改成文字圆章和字母头像，品牌识别度及与既有框架的一致性不足。
- 证据：两份原系统 HTML 都引用 `logo-af80dc69.png`，并在右上使用 `avatar-44b807e9.jpg`；当前样式以 `.seal` 的圆形文字和 `.avatar` 的纯色圆形实现。该差异不涉及轨道管理字段或流程。
- 建议：在已有、可授权复用的资源范围内换用同一 Logo/头像表现；若不能复用真实资产，保留当前占位并在规范中定义统一的“模拟品牌资产”版本，避免同一产品内混用图片与字母圆章。

### V-03 — 全局色彩需要有明确的标准化裁决【需处理】

- 分类：视觉
- 原意见：原系统快照的框架菜单背景为 `#353535`、主色变量为 `#165DFF`；当前原型顶栏为深蓝 `#08233f`、常用主色为 `#1767e8/#2a78ff`。这不是单纯抗锯齿差异，而是一套不同的全局主题。
- 证据：原 HTML 根节点的 Element Plus 变量及横向菜单内联变量可直接见到上述颜色；`src/App.css` 的 `.system-header`、`.module-entry.is-active::after`、`.primary-button` 定义了当前颜色。证据盘点只要求复用统一壳层，未授权改变框架主题。
- 建议：将此项作为阶段 2 的视觉裁决项：选择“忠实沿用原系统主题”或“复用任务规划系统的标准主题”。裁决前不应把当前颜色当作无差异的还原；裁决后把选定色值写入 `docs/ui-spec.md` 的语义令牌。

### V-04 — 图标语言混用，降低了壳层精致度【需处理】

- 分类：视觉
- 原意见：原系统顶部通知、用户下拉、侧栏分组均使用同一套 SVG 图标；原型在页面标签、设置和弹层关闭处使用文字字符，图标粗细、基线和可读性不稳定。
- 证据：原 HTML 中相关入口均为内嵌 SVG；当前 `OrbitTrackManagePage.tsx` 以单字符呈现页签关闭/设置，`OrbitTrackDialogs.tsx` 以 `×` 呈现关闭，`.close-button` 又将字号放大到 `24px`。该问题完全位于视觉表现，不改变入口位置或操作结果。
- 建议：使用项目现有的同一图标来源替换这些字符，并统一 16px/20px 的图标尺寸、悬停色与可点击热区；保留现有 `aria-label`。

### V-05 — 弹层的标题与内容层次可统一【建议，非证据缺陷】

- 分类：建议
- 原意见：定轨结果弹层同时使用“弹层标题 + 蓝色左边线小节标题 + 灰底数据块”，信息层级已经可辨，但历史弹层和配置弹层没有相同的小节规则；跨弹层的层级语法仍不稳定。
- 证据：`OrbitTrackDialogs.tsx` 仅结果弹层包含 `result-body > h3` 和多个 `result-block`；`src/App.css` 对这两类元素单独定义左边线、灰色块头。原始快照确认三个弹层的字段与入口，但未给出一条必须在所有弹层使用同样小节标题的业务规则。
- 建议：阶段 3 只沉淀可复用的“弹层头部/正文/底部、表单行、数据结果块”规则；不要强制把结果弹层的专业数据分区套到配置或历史表中。

### V-06 — 窄宽度仍需实测，当前不能作为通过项【需处理】

- 分类：缺陷
- 原意见：页面外壳声明 `min-width: 1024px`，主表又声明 `min-width: 1060px`（在较窄媒体查询时仍为 `980px`）；在 1024px 视口扣除侧栏后，表格只能依赖横向滚动。是否保持可读、是否出现双横向滚动尚未验证。
- 证据：`src/App.css` 的 `.orbit-shell`、`.data-table`、`.table-scroll` 和 `@media (max-width: 1100px)` 可直接核对；技能门禁要求检查 1440px、1280px、1024px，当前没有对应浏览器验证记录。
- 建议：在后续可用浏览器环境中逐个记录三种宽度的截图/结论，重点检查顶部菜单是否截断、侧栏是否遮挡、表格是否只有表格容器一处横滚。若现状符合原系统的桌面横滚策略，可记录为通过；否则再调整布局，不预设业务字段删减或重排。

## 结论

本次没有发现需要改变轨道管理字段、入口、导航或业务流程的视觉意见。进入阶段 3 前，至少应裁决 V-01（壳层尺寸）与 V-03（主题色），并完成 V-06 的三种桌面宽度实测；V-02、V-04 可作为不触及业务的实现修订项，V-05 仅作为规范编写边界。
